# 4.6 客户端加载等待诊断

## 已知现象与证据边界

2026-10-19 用户确认中文语音可选择、对白正常，随后报告进场景仍转圈、无法操作，并补充约 30 秒后会“自动停止”。这句话尚不能区分游戏自行退出、遮罩解除或画面停住。实际 PID 65628 于 02:18:22 启动、02:20:29 退出，独立日志读取器记录退出码 0。Unity 日志已经执行 `AdventurePhase._OnLoadingFinish`；`AvatarSkinHelper.TryGetAvatarSkinDataCache` 空引用属于 `OnApplicationQuit` 清理调用链，不能据此认定它造成转圈。最近两小时 Windows Application 1000/1001 查询未返回事件，也不能据此认定用户手动退出。

本次保存的脱敏 Unity 日志、来源摘要及只读原生分析在 `build/loading-blocker-20261019`。来源 Player.log 为 141,900 字节，SHA256 `b47de26d32600cefa615891fe4d1b60cba7be83333f670e28f8511c97df1e061`。日志没有保存遮罩正在等待的响应编号。原生代码存在 30 秒等待路径，与用户时长相符，但这只是候选机制，尚非该次故障根因。

## 自动记录范围

现有外部日志窗口就绪后，启动 `scripts/client-wait-state.py` 中的独立采样线程。它为同一 PID、同一创建时间重新核对 EXE 路径，校验 GameAssembly 和 metadata 摘要，再打开只读进程句柄。每秒最多采样一次，最多持续 600 秒；游戏退出或日志窗口结束后停止。它不注入 DLL、不调用游戏函数、不写入进程或存档，也不申请进程终止权限。

输出为 `%LOCALAPPDATA%/HKRPG/client-waits-日期-时间-PID-随机后缀.jsonl`，与普通 `client-debug` 日志匹配。文件独立写入并逐行刷新，控制台输出暂停不会阻塞这份记录。只保存时间、PID、加载/剧情标志、等待项数量、响应编号和超时上限；不保存内存地址、消息正文、账号或凭据。空闲状态去重，有等待项时保留每秒记录，用于判断等待结束、重复产生或一直不解除。

未匹配客户端版本时停止内存读取。对象尚未初始化、字典版本变化、无效指针、超长数组或非有限超时值时拒绝解释该次快照，下一秒重试。权限不足等错误只记录异常类型，不中断普通 Player.log 读取，不影响游戏。

## 版本与布局依据

只接受当前已核对的 GameAssembly SHA256 `8cc7380066343b6152069a6d1c90e230322aa78b780b1e738c13185b3692f1d3` 和 metadata SHA256 `09ce2093b78779d4bbe9dc866bb472438efd96cc6546b7cbc34edf4006736130`。

`UIManager.get_Instance` RVA `0xe3b5d90` 从全局槽 `0x93434a8` 指向的实例表取 `+0x1398`。类型 73076 的 `_FullScreenBlock` 位于 `+0xd0`；加载、剧情和卸载标志分别为 `+0x124/+0x12c/+0x12f`。`BlockWaitNetPacket` RVA `0xe3a7d00` 进入 `0x165b4c20`，构造种类为 2 的等待项，响应编号在 `+0x3e`、超时在 `+0x40`。`NotifyWaitNetPacketReturn` RVA `0xe3a7ed0` 查询等待字典 `+0x10`。第二个阻塞字典 `+0x20` 仅读取数量，不猜测其回调含义。

## 启动权限

当前游戏 EXE 需要管理员权限，而原桌面快捷方式的启动器没有管理员标志。有限进程查询能读取生命周期，但普通权限的记录器不能据此获得管理员游戏的内存读取权限。实际启动先在普通权限下只读检查服务器和七份客户端文件，通过后由 Windows 正常权限确认重新启动隐藏启动器，游戏和独立日志窗口随后继承相同权限。已经提升权限时不再次提示；失败或取消不重试，带提升标记仍无管理员权限时明确停止，避免循环。预览和仅修复模式维持原有权限行为。

原桌面快捷方式的路径、图标和内容未修改；仍指向本仓库启动器，因此下次启动自动使用这些脚本。没有重新安装进程内 DLL，没有修改七份游戏文件、运营配置、数据库或 Compose 运行产物。
