# 4.6 传奇挑战配置与进度存储范围

后续专用查询、入场和结算已接入，实际奖励/编队隔离和两次正常 H2 恢复已验证，见[专用入口与结算范围](local-legend-dedicated-entry-4.6.md)。下文描述的是 33 项组件检查阶段，不代表当前专用处理器仍未发布。

本轮接入 Java 配置目录和 Player 内的目标进度存储。仍未发布专用入场、查询或结算回调处理器；不能把这些基础组件算作完整可玩活动。

`LocalLegendCatalog` 在玩法资源初始化时读取原始 LocalLegendStageConfig、ActivityLocalLegendGroup、ActivityLocalLegendReward 和共享 BattleTargetConfig。保留 15 个关卡的组、难度、事件、解锁 Quest、区域、试用候选和原始目标顺序，以及 5 个组的实际模块、10 条奖励任务的原始分类与排序。实际资源存在并不打开活动时段。

35 个传奇挑战目标只接纳原始 ChallengeTarget/GreaterEqual 条件和合法正阈值。结算解析使用本机已核对的类别键 5，目标 id 必须属于当前关卡；进度按无符号 uint32 比较，不能用客户端 total_progress 降低原始门槛。缺少目标报告或只有其他统计类别均产生零完成位，重复类别/目标、外组目标和未知类别拒绝。目录保留次数、百分比及分数目标的不同源阈值，第 3 组的 10,000/18,000 计分门槛不套到其他组。

缺少全部三份活动表的旧资源包继续兼容。只提供部分活动表、缺共享目标表、重复身份或模块、未知难度、非法整数、重复目标/试用候选、缺引用、超过集合或文件限制时拒绝；失败加载不继续暴露上一次目录。读取边界为活动表各 64 行、目标表 256 行、目标/试用数组 32 项、单份 JSON 2 MiB。未执行战斗目标 AbilityName 的逻辑，也未把其他共享目标的效果算作新增支持。

`LocalLegendProgress` 保存每个实际已记录关卡的完成位、变化时间和冻结资源身份。查询不创建记录，零位不制造历史；不同组/难度独立，后续报告只合并新增位，重复位不改时间。重新排列目标或改变冻结资源后，旧记录保留并关闭进度读取，不把旧位重映射到新目标。非法位、倒退时间、错关卡对象、损坏存档也不能产生完成。

完成位是原始列表中的位置掩码。例如第 3 个目标达成是字段 1 的数值 4，不能发送已完成目标数 1。原生字段映射、报告字典键和静态验证边界见[目标报告说明](battle-target-report-4.6.md)。

33 项新增检查：18 项目录/目标解析、15 项存储/位掩码检查。夹具保留 173 条完整原始记录、源提交 724b139d8c9c32d12552eb95745a4fee72bfe48b 和四份资源 SHA。实际 Player/Morphia 两次保存与读取保持两组独立目标位；原生协议字节检查保留掩码 4。这些是新组件检查，未将调试中的夹具预期错误计作已有行为的失败回归。

完整服务构建、独立源码构建、既有 172 项 KCP 检查与 Dispatch 检查按最终验证记录核对。网络检查仍验证普通日常战斗和非法目标报告，并未执行传奇挑战战斗或发布这些新进度。下一步仍须绑定实际当前战斗、正式/试用隔离队伍、活动/剧情/难度门槛、目标完成 Quest、一次领奖和正常 H2 恢复，再做官方客户端入口和玩法验收。整组 BattleChallenge 任务的参数含义尚未完整核对，不猜测为“全部星级”完成。
