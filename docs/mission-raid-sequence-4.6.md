# 4.6 多阶段任务副本

本批接入原始 `40231001` 的两个主任务 `1021301 → 1021401`，保留 `TrialOnly [1021002]`、14 号普通换队限制、前置 `1021201` 和不同的后续主任务 `1021501`。资源来自固定提交 `724b139d8c9c32d12552eb95745a4fee72bfe48b`，22 份完整 Git blob、90 条完整原始记录和37个子任务逐条比对；原始入口、阶段顺序、条件、试用角色和脚本没有改成固定完成。

`MissionRaidSequence` 在实际进入时保存来源、主任务顺序和当前阶段，与副本、任务资源一同校验。第一阶段只接取 `1021301`。阶段完成需要有效主任务、原始结束子任务、其接取依赖链和实际服务器转场收据；未知依赖类型、缺失前置、取消记录或损坏阶段不能推进。第二阶段必须到达其原始开始楼层，由原始 `MultiSequence 1021301` 门接取，整个副本只有两个阶段均有完成证明才进入已完成列表。

原始 `102130113` 将服务器从 `40231001` 转到 `40231004`，`102140141` 再转到 `40231003`。这两步只解释完整的单一 `RPG.GameCore.RaidSceneTransfer` 图；混合脚本不能按一次空转场处理。第一阶段结束后，第二阶段原始 `102140142` 执行 `ReplaceTrialPlayer`，发布单人试用队伍 `1021213`；未接取的 `102140143` 不会自动创建 `1021204`。基础队伍与剧情队伍保持各自来源和独立状态。

暂离记录当前阶段和实际位置，恢复第二阶段时不重接第一阶段、不重复转场或创建角色。完成后的实际返回入口为 `2023202`，保存完成返回收据；不同的后续主任务仍按自己的原始接取条件处理，不由副本直接赠送。普通队伍和正式角色数据库不写入上述试用角色。基础试用队伍在剧情创建前和销毁后也通过全部/当前队伍查询一致返回；已选择的普通队伍编号1在副本视图中保留，不固定回0。旧的单主任务副本记录维持原有格式；缺少来源快照的多阶段记录不能自行升级成有效阶段。

34 项新增 Java 检查已覆盖原始资源接入、初始阶段、两次转场、第二阶段角色替换、未接取可选角色、完整结算、暂离重入、重复查询、并发刷新、损坏来源/顺序/前置/转场收据和未来阶段注入。两个实际 Player/Morphia 场景各读取两次，检查阶段0和阶段1恢复。入口、基础队伍查询及编号保留共六项实际行为回归在修复前失败，记录在 `build/multi-stage-raid-behavior-red.xml`、`build/multi-stage-raid-query-behavior-red.xml` 和 `build/multi-stage-raid-index-behavior-red.xml`；来源比对记录在 `build/multi-stage-raid-source-proof.json`。

本批新增 `scripts/smoke-mission-raid-sequence.py`，使用真实打包服务器、SDK 登录、UDP/KCP 请求及正常关闭后的 H2 恢复。前置主任务接取、第一阶段对话/战斗结果、第二阶段对话/战斗结果是在有明确标记的隔离数据库中设置的测试夹具。两个主任务原始开始/结束列表、全部37个子任务、原始脚本、角色、Raid行与楼层资源保持原件；实际转场、角色替换、阶段开放、暂离/返回和完整副本结算由服务器执行。原型已通过104个KCP请求、10份快照、6次正常关服、同UID的5次H2进程重启及9次离线数据库操作（6次只读检查、3次明确夹具写入），2,558份来源资源SHA保持不变。源码导出全量回归和同 jar 最终复验以 `build/multi-stage-raid-verification.json` 为准，封存记录仍区分原型与最终构建。
