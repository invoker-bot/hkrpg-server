# 构建和验证

Windows 使用 `scripts/build.ps1`，默认最多用 4 个独立 Java 进程分配测试类。
每个进程内保持顺序执行，以保留测试对静态游戏数据的隔离方式。
端口、数据目录及运营配置的隔离仍由现有测试负责，不能把共享文件改成同时写入。

`-TestForks 1` 可顺序运行；参数范围为 1 至 8，默认仍为最多 4 个进程。
本机批次可显式使用 `-TestForks 8`；各进程内仍顺序执行，Netty 选择器仍固定为两个线程。
`-RerunTests` 强制重跑测试，同时复用未改变的编译结果。
`-SkipTests` 只打包，不能作为完整验证通过的证据。
直接使用 Gradle 时，测试进程数量通过 `-PtestForks=1` 等参数设置。

2026-10-11 对同一批 479 个测试类、13,004 项 Java 测试进行了一次顺序和并行对比：
前一轮顺序构建 25 分 26 秒，4 个进程的构建 12 分 2 秒，耗时减少约 53%。
两轮均没有失败、错误或跳过。核对了 2,439 份编译输入未变，服务端 jar 也保持原字节；
并行运行复用了已经编译的结果。这是单次对比，不承诺所有机器或每轮构建都达到相同比例。
本地证据保存在 `build/parallel-test-verification.json` 和 `build/parallel-test-build.log`。

2026-10-12 显式使用 8 个测试进程的实际完整 Gradle 构建报告 15 分 31 秒，
520 个套件、14,226 项测试无失败、错误或跳过，2,584 份输入与候选包保持相同。
相邻的 4 进程批次为 926.0527 秒；这轮增加 120 项测试且同时执行隔离运行探针，
没有证据证明 8 进程更快，也不能据此作严格性能比较，默认继续保持 4。
实际日志包含八条测试工作进程启动记录；汇总脚本临时变量覆盖在 Gradle 成功后抛出异常，
因此没有保留其内存采样和进程峰值，不能把启动行数当成峰值测量。
原脚本与日志原样保留，随后仅凭实际新 XML 和前后输入哈希恢复验证报告，
没有重跑 Gradle。证据为 `build/feixiao-selected-item-blessing-console-full-verification.json`；
520 份 XML 原件在同名前缀的 `-full-xml/` 中完整归档。

验证时先用有意义的回归复现问题，再运行相关测试；最终修改固定后执行完整构建。
新修改、失败或尚未解决的风险才需要扩大或重复验证。
构建通过、服务端通信通过和真实游戏客户端验收分别记录，不能互相替代。
