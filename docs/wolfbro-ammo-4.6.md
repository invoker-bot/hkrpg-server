# 小小哈努普通枪械与弹药状态（4.6 实验路径）

本轮接入原始关卡中的枪械激活、普通射击上报、掉落拾取和弹药存档字段。初次取得弹药、每次上报扣弹、每个实际原始怪物产生一个拾取点，是本服明确制定的规则。客户端原件证明请求与状态布局，不证明这三项服务端数量规则就是官方规则。

## 原件与请求

固定数据来源为 TurnBasedGameData `724b139d8c9c32d12552eb95745a4fee72bfe48b`。运行时核对 86 份完整原始文件和 41 条完整原行。关卡目录共有 17 条，关卡 16 的原始 G11 文件在固定来源和已安装资源中缺失，该关卡不能据此宣称支持。

- 激活请求 6525 使用实际消息的 group 字段 12 和实例字段 7；只接受当前已加载的原始枪械道具 103068。
- 普通射击实际发送 6514，消息为 `OKEFGCNNEKI`，实体列表在字段 1。空列表也是一次射击。实际普通发送器不写可选 Vector 字段 14，本轮对额外传入此字段的请求拒绝处理。
- 拾取请求 6508 的坐标在字段 6。只接受本次运行已持久保存的掉落坐标，达到原始上限 5 时不能增加。
- 状态通知 6548 与查询返回保留实际激活、弹药数、拾取点和独立存档字段。未激活时不制造弹药，重复激活不补满已经消耗的弹药。

6514 的固定命令枚举是 `CmdWolfBroType_HPHNFDIPEIE`；命令清单没有它的语义名称，因此入口使用已经核对的数值分支，没有改写原描述符或生成协议类。爆炸上报 6502 的实际发送器也已静态核对，但本轮尚未实现其玩法。

## 持久状态与原始场景

弹药账本绑定玩家 UID、运行 UUID 和全部所需原件身份。动作前核对磁盘原件、实际加载的完整 Floor/Group、Excel 和实体实例；小型状态才允许操作枪械。资源比较遵循真实 `ResourceLoader` 的 `PropExcel.onLoad()`，同时保留加载前完整原行校验。

射击先验证全部目标，再保存扣弹、击败凭据和拾取点，保存成功后才移除实际怪物。保存失败恢复旧账本；拾取与存档恢复同样保留失败回滚。已提交的击败凭据抑制相应原怪物在组重新加载时复活。恢复存档保留已经发生的击败和首次填弹凭据，不通过重放枪械取得第二次初始填弹。

本轮目标校验采用原始出生坐标和原始事件 ID；移动后的怪物、完整 AI、爆炸及全部关卡机关不在这个已实现范围内。此限制仍须继续补齐。

## 验证边界

早期 18 项请求回归和后续单项加载检查的夹具，在把 `PlaneName` 转为已加载标量时误改了原始表对象；相关断言不能计作弹药行为 RED。原日志和 XML 保留，报告已补充 `sourceFixtureInvalid` 归因。源表改用完整独立副本后，`build/wolf-ammo-source-valid-red-verification.json` 的两项检查中，原件正向通过，实际 `PropExcel.onLoad` 归一化回归产生一项纯断言失败；运行时源副本现执行同样的 Prop/Floor 加载归一化，完整来源校验保持。

`build/chess-ammo-service-corrected-red-verification.json` 保存另一组真实失败：27 项弹药回归中的五项非空射击被拒绝，原因是共用校验器只接受未打包标量，拒绝了 4.6 proto3 的合法 packed 实体列表。弹药入口改为同时接受 packed 与 unpacked uint32，在使用解析后的实体 ID 前检查原始完整 varint；另补混合编码和溢出值不得别名实际 NPC 的回归。旧关卡恢复仍保持没有弹药变化时的原 Run 对象身份。

本机静态核对最新报告 `build/wolfbro-ammo-client-original-number-tokens/verification.json` 通过 439 项检查：10 个类型、28 个完整 PE 函数、两份完整客户端配置解码及整对象固定源比对、关卡 11 的六份完整文件和 30 条完整原行、127 个运行时来源摘要。这些检查没有启动游戏，没有提供客户端界面验收。
