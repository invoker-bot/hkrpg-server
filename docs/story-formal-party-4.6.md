# 剧情正式角色与编队恢复

本次处理的是任务记录、角色文档、队伍文档分别保存造成的缺人和卡任务。不能把本次修复视为所有剧情演出或全部试用脚本已经完整实现。内部协议基线仍为 LunarCore lite 4.2.0，4.6 为实验兼容层。

## 原因与实现

- 醒来对白 `100020103` 完成后，旧实现没有发放三月七。兼容规则现在在原始任务、完成记录、已选主角身份都吻合时，补发正式角色 `1001`，并执行一次加入队伍。原始客户端脚本仅包含完成回执，没有服务端发角色参数；本规则明确属于兼容实现，不伪称找回了原始服务端脚本。它会修复满足条件的旧存档，不跳过对白、不重置进度，也没有 UID 特例。
- 电梯对白结束后的主任务 `1000201` 原奖励 `11000201` 包含丹恒 `1002`。角色领取成功后执行一次入队，后续 `100020133` 的原始 `ChangeLineup [8001,1001,1002,0,1001]` 可以正常组成三人队并切换队长。
- 正式角色奖励采用持久化发放意图和预留角色文档 ID。角色已存在时保留其等级、经验、装备和身份；数据库已写入而请求中断时按预留 ID 读取，避免重复创建。角色头像也必须保存后才能标记发放完成，避免登录过程中只更新内存而重登丢失。普通物品、信用点等仍使用原防重领奖账本，不会因为恢复角色而重发。
- 当前资源中三类正式角色任务奖励（丹恒、娜塔莎、黑塔）均经过同一发放流程。只有已明确的开场同伴规则自动入队，不把所有获得的角色都强塞进当前队伍。黑塔同一奖励中的第六栏光锥原来未被 `RewardExcel` 读取，已补全第六栏并锁定原始资源回归。
- 编队先保存来源及变更前后的完整队伍，再保存队伍，最后保存完成记录。中断可以继续；来源变化或队伍已经被其他操作改写时不会盲目覆盖。原始 `ChangeLineup` 的任务完成回执已接收但保存中断时，由任务刷新接续，不要求客户端凭空重播一次事件。其他非幂等剧情动作和旧的无来源挂起回执不会被任意视为完成。
- 已执行过的自动入队不会在每次登录时重放。满队时保留现有成员；战斗、额外队伍、临时试用队伍中推迟普通编队变更。退出后才恢复。任务角色发放时机与头像解锁的登录加载顺序也已对齐。

## 来源和验证边界

固定数据来源为 [TurnBasedGameData](https://github.com/DimbreathBot/TurnBasedGameData/tree/724b139d8c9c32d12552eb95745a4fee72bfe48b)，提交 `724b139d8c9c32d12552eb95745a4fee72bfe48b`。部分任务定义使用本项目已安装的匹配客户端提取文件。回归夹具保存完整相关任务和原始奖励行，以及来源文件 SHA-256。三月七补发仍是有明确条件的兼容规则，其客户端入队呈现需要独立验收。

`StoryParty46Test` 使用独立数据库验证漏发修复、三个原始角色奖励、重复执行、已有角色、两次文档重载、各保存边界中断、已写入但未发布的角色、源定义变化、满队及临时队伍、原始三人编队恢复。`StoryLineupTest` 验证队伍保存失败回退、动作游标恢复、变更来源及队伍冲突。原有任务奖励和剧情算术回归继续保留。

可复现检查：

```powershell

./scripts/build.ps1
python scripts/smoke-opening-stage-win.py --readings --ambush --avatar-progression --space-anchors --story-party
```

资源盘点覆盖 17,882 个子任务、3 个正式角色任务奖励来源、1 个原始编队动作及 17 个试用角色条件。新增来源、奖励栏位或动作发生变化时盘点会失败，要求补充验证。17 个试用条件的清单不代表所有演出已通过实机验收；原有试用生命周期的能力边界见 `mission-trial-lifecycle-4.6.md`。

原生 KCP 探针使用独立新号和独立 H2 数据库，经开场对白、三月七入队、战斗、丹恒奖励、原始三人编队、手动修改队伍，再重连及正常停止后的 H2 重启。对白和战报是合成请求，不能据此声称官方客户端动画、按钮及全过程已实机通过。正式账号仅做保存保护与更新后的只读核对；最终客户端呈现仍以用户重新登录后的结果为准。
