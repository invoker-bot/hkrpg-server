# 剧情动作与任务领奖保存失败恢复

本轮继续检查剧情动作、普通任务及每日目标的共享保存路径。新增的故障测试只在隔离副本和临时 H2 中执行，不改变正式玩家进度。

## 已修复问题

1. `StoryActions` 在动作预约的首次保存失败时，普通动作尚未执行，内存却留下 pending，后续请求永久返回忙碌。现在撤销尚未进入执行阶段的预约；本次新建且没有已完成步骤的空游标移除。已有游标及本次请求中先前成功保存的步骤保留，重试从原步骤继续，不重复加值或投递物品。
2. 普通任务和每日目标在首次领奖预约保存失败时，尚未投递物品，却留下 CLAIMING。现在恢复同一 QuestState 对象的 FINISHED、进度和完成时间，保留观察标识，允许原请求重试。
3. 两个领奖入口在最终完成保存失败时，内存曾继续显示 CLOSED，可能让后续查询错误地认为已经确认领取。现在恢复 CLAIMING，保留实际投递和对应的当前积分，拒绝自动重发。

`QuestRewardWrites` 集中处理两个领奖入口的阶段保存。调用方继续持有玩家锁；部分投递、投递中断，以及已经保存的 pending 动作不会自动清空。编队动作沿原有来源绑定规则恢复。动作已执行后未保存完成游标的情况继续保留原有防重边界，不伪造跨文档事务或崩溃后安全重放。

## 日志

`Story action interrupted` 记录子任务、从零开始的动作序号、固定阶段及异常类型。阶段区分预约保存、执行拒绝、执行异常、完成保存和已有 pending 游标。

`Quest reward incomplete` 记录目标、奖励、固定原因和 CLAIMING；`Gameplay save failed` 的 `quest-reward-reserve` 与 `quest-reward-complete` 区分两个保存阶段。相同目标和原因沿用每分钟首次详情、重复次数及超额汇总，不输出原请求、账户、收据正文或异常消息。

## 验证边界

修改前的隔离回归为 18 项，其中 12 项按预期失败，6 项部分投递或已执行动作的防重控制通过。四项使用实际 Player 与 GameItem 文档，故障后再作一次正常保存，再正常关闭和重新打开 H2，核对阶段与实际物品，确认后续正常保存不会写入错误的内存阶段。新增两项日志检查验证不同目标、步骤、阶段可分别定位，同类重复折叠且异常消息不泄漏。
