# 跃迁网页异常残留与 Esc 失效

## 现象与证据

2026-10-26，真实客户端能通过鼠标打开手机菜单，但按 Esc 无反应。后台日志窗口显示
`from game wnd ESC KEY DOWN`，调用源为 `MiHoYo.SDK.BrowserWin32Helper.wndProc`。
这不是日志读取器消费按键的证据：固定客户端的该分支在 SDK 网页声明接管 Esc 后记录日志并返回 1，跳过默认窗口处理。

本次 `Player.log` 同时记录了完整的前因：

1. `OpeUtil.OpenGachaHistoryURL` 创建 SDK WebView。
2. 随后的 `MiHoYoSDKWebView.QueryParameterInUrl / Load` 抛出 `System.UriFormatException`。
3. 这一个 WebView 没有对应的销毁记录。之后公告创建的另一 WebView 能正常关闭，不能证明旧窗口已清理。
4. Esc 没有产生手机菜单请求；鼠标打开手机成功，排除了整个手机功能未解锁这一解释。

源代码与异常一致：4.2 的 `GachaBanner.toProto` 显式填写空网址，4.6 的 `GachaInitial46` 则省略了两个网址。
客户端先创建窗口，再解析网址，因此空值会在窗口注册后触发异常。

## 修复边界

- 两套协议均提供本服 HTTP 服务的绝对网址，使用配置的公开域名、协议和端口，并支持 IPv6。
- 4.6 的 `detail_url` / `history_url` 对应 wire 6 / 12；已对照固定客户端的 `WriteTo` 与 `SyncGachaPoolData`，没有手改生成协议类。
- `/gacha/details` 与 `/gacha/history` 在 Dispatch 和 Game HTTP 服务均可访问，不依赖 GM 登录、第三方页面或外部脚本。
- 页面是明确说明尚未支持功能的静态页面。本批没有新增逐次抽卡历史或完整概率详情；不能把“尚未保存记录”展示为“从未抽取”。
- SDK 附加的账号参数不被页面读取、回显、转发或用于查询存档。访问页面不抽卡、不扣款、不修改保底或背包。
- 修复阻止后续空网址再次制造残留窗口；已存在于客户端内存中的异常窗口是否能通过正常页面关闭或返回标题清理，需要单独实机确认，服务更新本身不等于清理成功。

## 验证记录

- 修改前两项行为回归真实失败：旧/新协议网址均为空；HTTP 页面返回 404。

- 隔离原生 KCP 初始化探针读取实际 4.6 报文的两个网址，检查公开 HTTP 源与页面响应，并在 H2 重启后复验；不使用运营玩家做抽卡实验。
