# 菜单依赖查询与重连恢复（国服 4.6）

## 已确认的缺陷

`GetMissionStatusScRsp` 原来只返回请求中已完成的主任务，其余主任务没有答复。
本机客户端 `MissionModule._UpdateMissionStatus` 会为返回的每个主任务调用
`_UpdateMainMission`，更新完成标记、兑现该任务的数据等待对象，并从待准备集合移除。
`_TryFinishDataPreparation` 只在集合为空时发出准备完成事件。因此返回一个成功但不完整的
响应并不等于完成初始化；重连时仍可能留下未解决的菜单、剧情依赖。

另一个缺陷是状态查询调用 `MissionManager.refresh()`，可接受自动任务和执行剧情动作。
查询解锁条件不应推进进度。原有游戏事件和全量任务刷新仍负责推进任务。

## 修复边界

- 请求中的每个主任务均返回已完成或未完成状态；未接受任务明确返回未完成。
- FINISHED、CLAIMING、CLOSED 的既有有效完成记录保持完成状态。
- 在玩家锁内读取一致状态；查询不再刷新或保存剧情进度。
- 不重放历史完成通知，不预先解锁新号功能，不改写正式玩家任务或背包。
- 4.6 仍通过协议桥转换；未手工修改生成协议，完成列表为字段 14，未完成列表为字段 3。

## 实机发现的图鉴初始化断线

第一轮部署后，同一个 `StarRail.exe` 进程（PID 72708，启动时间
2026-10-25 01:51:17 +08:00）恢复了商店、队伍等图标，但随后反复自动重连。
服务日志明确记录 `GetArchiveDataCsReq` 的回复因 `ArchiveData.monster_list`
无法转换而被拒绝。因此仅恢复图标不能算通过，必须同时确认初始化后的连接稳定。

同一固定客户端的静态调用也证实这条顺序：`ArchiveModule._OnMainMissionDataReady`
（RVA `0xc692010`）在未准备时调用 `GetArchiveDatas`（`0xc6917f0`），后者发送
2334。接收方法 `0xc692200` 消费图鉴容器后设置准备标记并通知更新。
实际回复类型 `JPMDALGBLBO` 的容器/结果字段常量为 4/8，与固定协议一致。

原图鉴回复从资源目录构建非空怪物、遗器和光锥集合。它仍是继承的全目录快照，
不能把它描述成玩家实际收集或击杀记录，本轮不改变这个既有行为。

依据固定参考 `March7thHoney-OpenSource@fe00bdbda3c28ca33d01f171566aa35b5ab95083`
的 `Proto/4.6/CmdArchiveType.proto` 与 `PacketGetArchiveDataScRsp.cs`，补齐三个语义映射：

- 怪物集合：`ArchiveData.monster_list` → `kill_monster_list`（4.6 字段 13）；
  子项怪物编号/次数保持字段 2/6。
- 遗器套装：`RelicArchive.relic_id` → `set_id`（字段 3）。
- 遗器部位：`RelicArchive.slot` → `type`（字段 15）。

回复命令仍按匹配表转换到 2325，外层图鉴容器为字段 4、结果字段 8。
光锥编号保持字段 12。没有用空成功回复绕过错误，也没有放宽未核实字段的拒绝规则。
映射独立实现，未复制参考仓库代码、未引入参考运行时或修改生成协议。

`ArchiveReconnect46Test` 五项回归中，三个非空行为用例在修复前复现失败；
另两项保护未知字段拒绝和空查询的路由。修复后同时验证怪物次数、套装/部位不互换、
光锥编号、三次回复不变以及 4.2 原始字节不变。
