现阶段按领域隔离代码，不急于把同一套反射模型拆成多模块。业务状态与通知已有大量领域关联；拆包和拆进程应以实际依赖与部署需求为依据。

## 协议边界

场景动作的原生入口由 `SceneActionWire46` 先检查线格式，阻止重复单值字段、溢出编号和未知嵌套字段在 protobuf 解析时被合并、截断或忽略。`SceneCastRequest46` 集中解释 Ability UseID 与实际施放实体，按当前场景实体类型归并命中/辅助列表，完成最终边界检查后才交给技能和战斗服务。错误通过 `SceneActionDiagnostics46` 记录限量元数据。验证及兼容边界见 [场景动作入口](scene-action-admission-4.6.md)。

探索资源安装包含ConfigAdventureAbility全部子目录、ConfigAdventureModifier、ConfigSummonUnit、ConfigMazeBuff和ConfigEntity/SummonUnit；追加安装只增加文件和独立补充清单，遇到运营文件冲突在复制前拒绝。74条召唤定义中的28条服务端配置由实际加载器读取，46条客户端定义不创建服务端配置实例。当前场景仍是单召唤物模型，登记、替换、超时、直接移除和按DestroyOnEnterBattle销毁已有回归；持续时间使用有符号int32毫秒和-1永久标记，超出表示范围不能先删除原实体。CreateSummonUnit明确固定时长叶任务和DestroySummonUnit的Caster/编号选择器已接入；缺省/动态时长、位置偏移/导航、条件分支、创建/销毁脚本、完整触发器、唯一组及多实例规则仍待接入。

角色探索Buff在有效战斗入口形成固定快照，正式和试用角色均按当前实际槽位绑定。战斗查询使用该快照；未开始的预览仅构造临时数据，不改变战斗缓存或角色效果。明确声明AddBattleBuff、角色技能绑定和非空绑定键的一级效果结转后消耗并通知真实场景角色；其他消费语义仍待逐项核对。角色绑定使用独立列表保留不同施法者及同编号显式战斗效果，既有按ID查询接口保留首个可用实例；NPC多施法者、完整动态参数、修饰器与跨场景生命周期仍待完成。

`MazeBuffExcel` 注册必需的基础 `MazeBuff.json`，以及可选的 `RogueMazeBuff.json`、`AvatarMazeBuff.json`、`AvatarMazeBuffLD.json`，以原始ID/等级合并到同一缓存，并保留角色表的ModifierName、MazeBuffType和UseType。加载器只跳过不存在的可选表，存在但格式错误仍报告失败；角色分表不能代替必需的基础表。启动预检从注册表中剔除可选名称，不把4.6拆表强制施加给旧4.2资源。当前4.6角色分表分别有148/4行，233项经典一级祝福均有可构造定义（161项无解锁列表），最终候选仍受玩家解锁和已有记录约束。资源范围不代表全部战斗效果、Buff消耗和修饰器生命周期或游戏客户端验收。

`RogueDownload46` 使用已核对的原生 1864/1821。`RogueDownload` 只接受当前资源休息房的实际 1001 装置与已持有的正式角色；下载角色加入 `RogueRun.vitals`，不自动改变出战 `roster`。新局保存 `initialAvatarSp`，不随天赋或资源重载刷新下载能量；旧记录缺少此快照时拒绝。`usedDownloadConsoles` 按站点/房间/组/资源实例保存，场景实体编号重建不会再次使用，`UniverseEntityLoader` 恢复 Locked 外观。角色状态和装置标记在同一玩家文档保存。每局每台一次下载一名采用本项目规则，额外编号列表和特殊上限未确认，试用/剧情角色与游戏 UI 未验收。

`RogueEnhancement46` 单独解析已核对的经典 1885 字段 13，并通过 `GameSession.sendClientPacket(int, byte[])` 发送 1807 的字段 3/6；冻结命令表中的同名 5484/5469 属于另一模式，不能复用。`RogueEnhancement` 核对实际休息房黑塔及资源实例；首次报价写入 `RogueRun.enhancementPlans`，购买在同一玩家文档保存余额、二级祝福和完成标记。旧记录需要合法查询后取得报价，资源重载不改变已有价格。仅覆盖一级到二级及本项目基础价格，客户端布尔字段和 UI 未验收。

`RogueEconomy.initialCoins` 严格读取 `Start_Rogue_Coin_Base` 的非负整数，只在新局初始化一次；暂停、重连、资源热更和存档恢复均使用已有余额。4.6 原生开始要求有效资源值，当前固定快照为 50；缺失、负数、小数或溢出拒绝。内部旧版领域模型在完全缺少该资源时保留原 100 默认值，仅用于兼容，不能通过 4.6 开始入口。零是有效资源值，不回退到旧金额。

`Battle` 完成加载参战 NPC 后调用 `UniverseManager.onBattlePrepared`，冻结实际当前场景对象、组/实例、资源怪物/关卡及本项目基础碎片数量；基础构造函数早于 NPC 加载，不能在那里统计数量。成功结算核对冻结对象，参战集合或身份变化拒绝；只在服务器确认胜利后创建 `RogueCombatGrant`。金额、已入账状态和战斗防重键同属一个玩家文档，局部清怪也立即保存。整数溢出保留已确认但未入账的金额，后续查询在当前探索中按冻结数量重试；未确认胜利和缺少记录的旧存档不补算。完整战斗跨进程恢复、终局后溢出金额、官方掉落配方仍未实现。

`RogueRevival` 仅支持资源明确给出的经典装置 1002 与恢复计数 0、效果 1；新局在同一玩家文档冻结碎片单价及生命比例。实际当前场景、房间入口/组、装置状态和所有倒地目标先整批预检，再一次修改碎片和独立队伍生命并保存，能量/秘技点保持原值。每名角色消耗单价属于本项目规则；原生 `RogueRevival46` 同步费用并在查询、重入和成功响应使用相同快照。缺少计划的旧记录不从新资源推算费用，也不启用免费复活；其他计数/效果变体与天赋折扣未接入。

经典宇宙的终局结果单独保存在玩家的 `rogueResults`，当前探索以运行 ID 引用结果；开始新局不丢弃旧局尚未结清的首次奖励计划。结果快照和发放预留先于库存回调保存，发放成功后的真实 ItemList 用冻结内部协议保存。原生通知按本机字段证据转换，胜负与客户端运行状态分别表达；场外 Quit 确认后不再恢复展示。跨文档事务、部分发放自动对账和完整游戏客户端验收仍待完成。

`RogueEconomy` 在终局冻结清理房间的资源分数和十进制兑换点数；`rogueResults` 保存原计划和入账标记，天赋点余额与标记在同一玩家文档保存。`RogueTalents` 根据资源入口、前置集合及真实余额激活节点，扣点与激活一同保存。物品增加先持有玩家锁、再进入库存锁，保持与玩法操作一致的锁顺序；虚拟物品 32 入账采用同一余额，`RogueCurrencies` 分开保存 33/34 的真实余额并检查资源上限。`RogueTalent46` 发送原生列表、进度和三种货币状态，4.2 生成类保持不变。`RogueTalentEffects` 按资源初始化独立队伍能量、满血与秘技点，冻结 11/21/32 的已生效节点和每局重置价格。普通祝福组 100005 递归核对成员；开局额外候选、菜单价格/候选池/已展示集合/重置次数存入同一 `RogueRun`。原生重置不移除当前菜单，回调更新实际候选和次数，扣费与菜单一次保存；资源重载和中途激活不重置价格或次数。其他战斗/命途天赋效果仍待接入；旧结果缺少快照不自动推算。

`CycleScoreManager` 按资源起点、七天间隔和国服 +08:00 时间生成左闭右开周期。终局冻结原周期与分数，`cycleWeeks` 的积分和终局入账标记一同保存；延迟结清不能迁到新周。经典宇宙以实际房间分数贡献周期积分属于本项目规则，不宣称官方加成。领取整批先预检并冻结数量，再使用唯一账本；查询中的已领档位由成功账本或明确丢弃标记生成。单独奖励 110 超出资源容量时保留待领计划，`CycleScore46` 发送容量超限档位；客户端明确丢弃只关闭这笔未入库奖励，不删除已有物品。玩家锁先于库存锁；其余部分发放保留预留等待核对，尚无跨库存文档事务。其他宇宙模式计分、官方规则和真实 UI 未验收。

设计目标为 4.6.0 正式版。协议 ID、字段号、加密/帧格式和客户端资源作为同一版本交付单元。`ProtocolBridge` 用独立描述符和命令表转换消息，按语义名称及已审查别名重新编码；缓存响应、原始发送、HTTP Dispatch/Gateway 均经过版本边界。领域服务继续使用既有 Java 请求对象；4.6 新增命令由 `VersionedPacketHandler` 接入领域管理器。没有修改 `GameConstants.VERSION` 或手改生成类。

旧配置保留 4.2.0；显式选择 4.6.0 后启用实验协议。服务报告区分设计目标、所选线协议和客户端验收。未知命令、核心请求缺少映射、已填充的未映射响应字段会拒绝并关闭会话；不把半完成的登录保持为 ACTIVE。详见 [4.6 协议设计](protocol-4.6.md)。

本次保存的最新协议来源用于差异分析；不混用不同项目的同名消息。处理器名称差异清单仅是移植入口，并非字段兼容证明。

## 任务和奖励约束

应将任务状态持久化为 `locked -> accepted -> in_progress -> completed -> rewarded`，将剧情任务与 Quest/Achievement 分开，并由战斗、场景交互、物品变化等事件驱动。客户端报告只能推进允许客户端完成的目标。结算和奖励领取必须有玩家串行执行或事务/唯一领取键，确保重试不会重复发奖。状态变更与通知使用同一领域结果，不再在响应中强行返回完成。

当前 `QuestState` 持久化 DOING/FINISHED/CLAIMING/CLOSED。同玩家串行领取，在发放前保存 CLAIMING，防止并发、重试或重启后重复发放；玩家状态与背包仍是独立文档，中途失败保留待核对的 CLAIMING，尚无自动对账或补发事务。这种状态向客户端表现为待领取并返回忙碌，不假装奖励已到账。

## 部署与扩展约束

`GameplayState` 嵌入玩家文档，保存主/子任务、每日周期与活跃目标、登录活动、宇宙探索及奖励预留。领域管理器在玩家对象上串行修改，4.6 原生通知与核心消息转换分别处理。战斗动作与结算也使用同一玩家锁。场景组读取任务 Accept/Finish 条件，未知脚本不会默认完成；支持范围和操作方法见 [4.6 玩法](gameplay-4.6.md)。

`MessageManager` 用固定手机消息图验证已接取段落、回复分支和资源终点；剧情批量提交先全量预检，再保存同一玩家文档中的历史、候选和完成状态。等待天数保存接取日；获得物品列表保存已获得 ID 集合，避免重新查询计数。`StoryActions` 只执行固定资源中已确认的完成动作，以持久化游标阻止中断后的重复副作用；编队动作仅支持已持有的正式角色，并更新实际场景角色缓存和通知。`Story46` 发送楼层/组属性/组状态通知，场景快照读取玩家保存值。`UniverseEntityLoader` 按分配房间加载实体，`UniverseManager` 保存祝福批次并绑定实际战斗增益。`RogueLineup` 直接读取玩家文档内的探索编队/生命/能量/技能点，避免覆盖普通队伍或其他挑战的生命值；当前探索和返回位置均存于同一文档。`Universe46` 接入原生基础开始/重入/离开/放弃、查询、祝福与房间/地图同步。基础流程已通过真实 KCP 与暂停后的 H2 重启恢复；命途、特殊角色列表、完整结果展示和游戏 UI 仍待验收。`RogueUnlocks` 解释已确认的资源解锁规则并检查实际通关/祝福历史；`RogueMiracles` 只执行已核对的奇物效果子集，未实现的效果不进入候选。`ActivityAccess` 统一开放窗口/解锁检查，`MusicManager` 保存关卡结果并通过奖励账本发放新星级档位；`MusicComposition` 校验资源歌曲、预设、轨道位图、音效和剧情门槛并持久化，原生字段由本机调用与序列化交叉核对；客户端上报结果尚无输入重演验证。资源脚本加载与完整脚本解释器是独立交付项，不能用前者代表后者。

目前只提供本地默认配置。外网部署需完成 P5 对应检查与身份认证改造。Dispatch/Game 模式允许独立启动，但当前代码仍需要分别明确 HTTP 地址、数据库和 Region 注册，不能称为完整分布式集群。插件接口继承自 LunarCore API 1；不要在插件中绕过玩家状态一致性处理。

`SceneInteraction46` 区分原生配置编号和 UInt64 上下文，`SceneInteractions` 校验受支持的资源状态转换并保存普通场景物件状态。`SceneAnchors` 将配置初始开放与玩家激活记录分开，`SceneMap46` 读取基础地图/锚点状态并检查传送前置。`RoguePortal` 绑定运行、源站点/房间与实际目标，`Scene46` 在原生场景消息补充目标信息，开闭由当前清房/待选/战斗状态决定；旧楼层快照不能复用当前实体 ID。上述模块仍为部分流程，不处理未确认的费用、机关、完整探索地图和内容/故事线变体。

`ShopPurchase46` 处理 4.6 商品购买的 1505/1575 请求与回复，复用 `ShopService` 扣费和实际到账检查，避免内部未分配的回复命令导致星琼补票等待。来源、正常重启验证和未覆盖的商店机制见[跃迁星琼补票](gacha-ticket-exchange-4.6.md)。

`ShopService` 统一游戏内货币购买、自选奖励展开、唯一物品与容量校验。`ShopPurchaseState` 保存累计购买次数和未完成付款记录，`ShopCosmetics46` 提供已购名片及帕姆服装的查询和选择；现有多文档存储不提供跨崩溃原子性，异常记录不自动重复扣款。全目录检查和客户端边界见[商店购买说明](shop-purchases-4.6.md)。
