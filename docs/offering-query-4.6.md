# 4.6 供奉批量入口

原先实验协议只接受供奉 6、12 的限定组合，本机 4.6 客户端的
`OfferingModule._GetOfferingInfo` 会遍历供奉类型表，一次发送所有编号。
现已接通固定来源中 1 至 15 的单项及批量查询，保留请求顺序。
原有单独查询 6、12 和混合查询 6、12 的路径继续保留。

供奉 6 读取已支付材料、实际等级、剩余经验和已领奖收据；供奉 12 使用既有骰子供奉状态。
其他编号尚未接通的结算不借用这两套进度，不写入最高等级或已领奖记录。
查询不会扣材料、发奖励或保存新供奉进度；未知存档进度会拒绝，不自动覆盖为零。
未接通编号的提交和领奖继续拒绝。

任务门槛按原始 `FuncUnlockData` 的六条配置读取：
既有主任务完成、子任务完成及其父任务记录须匹配，取消、缺失或损坏的记录不解锁。
没有任务门槛的编号可以查询；带 `ActivityModuleID` 的编号还要求运营配置中
唯一匹配、当前有效且面板可用的活动窗口。这里保留服务器的活动窗口约束，
没有把它当成已经验收的官方客户端全部活动规则。

批量查询先完成整批校验，再发布结果。
重复/未知编号、越界 uint32、截断、未知字段、损坏的供奉 6 或骰子状态、来源变更均不会返回部分成功。
合法的压缩和非压缩 uint32 列表都接受。解析缓存每次仍核对当前文件字节，
相同文件大小和修改时间不能掩盖变更。

资源来自 `TurnBasedGameData` 固定提交
`724b139d8c9c32d12552eb95745a4fee72bfe48b`。
夹具记录了 9 份完整文件的 Git 原文和本机资源 SHA，
运行时核对 5 张表的 44 条相关记录及 5 份完整文件的规范化 SHA。
供奉类型表包含 15 个编号，页面表有 14 行；没有为缺失的骰子页面补造配置。
主任务及子任务的加载定义与原始记录一起校验。

客户端只读证据来自用户提供的当前游戏目录：
`GameAssembly.dll` SHA 为 `8cc7380066343b6152069a6d1c90e230322aa78b780b1e738c13185b3692f1d3`。
原始方法编号 609674、RVA `0xd9d74f0` 的只读反汇编显示按表枚举并追加行 ID；
类型 14291 的 `OfferingTypeConfigRow.ID` 位于内存偏移 16，
类型 14292 的方法 96202 提供表枚举器。
内存偏移没有作为 wire 字段号使用；查询复用现有核对过的 4.6 命令和字段。
具体静态记录保存在本机 `build/offering-client-get-query.json` 等文件中。

定向验证：新增 22 项 Java 回归，第一批 16 项中有 11 项在修改入口前真实失败；
初次测试代码的访问权限编译错误不计入行为回归。
正常查询、任务门槛、取消/损坏记录、整批拒绝、两种列表编码和暖缓存篡改均覆盖。
完整构建包含 480 个测试类、13,026 项 Java 测试，无失败、错误或跳过，
4 个独立测试进程耗时 11 分 29 秒；2,444 份编译输入在验证期间保持不变。
42 次实际 KCP 请求中含 12 次整批拒绝，三次同 UID 会话覆盖重连和一次正常 H2 重启，
保留原供奉 6 的实际 18,800 份材料支付、50 级奖励及背包记录。
新目录先复制原测试数据库，查询前没有补写供奉进度；原数据库及九份来源文件未改。
两次服务退出均走正常停止。结果记录于 `build/offering-query-verification.json`。
新增剧情文件第一次未加入旧测试夹具而被拒绝，补入隔离夹具后通过；
没有放宽运行时对原始文件存在和来源的要求。

没有重复整套 Python 回归。客户端 DLL 与元数据文件 SHA 在本轮只读复核一致。
