## 确认的问题

1. `RewardLedger` 首次预约保存失败后，尚未执行任何物品投递，却在内存留下 pending 收据，相同请求无法重试。现仅撤销本次未进入投递阶段的预约；若物品可能已经投递，继续保留防重预约。
2. 物品写入成功、领奖完成标记保存失败时，内存仍可能显示 granted。只读 `granted` 也没有取得玩家锁，可能在保存尚未返回时读到完成。现失败后恢复 pending，查询与领取共用玩家锁，已投递物品不自动重发。
3. 普通对白、交物、首次演出关联目标和显式完成动作，在最终任务保存失败后仍留下 FINISHED 状态、分支选择和奖励计划。现对本次进度、时间、选择及新计划回退；同一接取对象和观察标识保留。此前已保存的动作游标、已确认扣款和独立物品写入不回滚，重试沿原凭据继续。
4. 普通首次演出的目标名单预约或最终完成标记保存失败后，未落库的记录仍可留在内存。现失败的初次预约移除，最终完成采用替换后保存，失败时恢复此前未完成记录；已经保存的子目标完成仍保留，后续重试不重复发奖。

完成写入集中在 `MissionCompletionWrites`，调用前的独立动作仍由原有游标负责。对初次交物预约失败、不能确认是否发生扣款的既有保守策略保持不变，不把这种明确保留 pending 的行为改成自动重扣。

## 诊断

新增 `Gameplay save failed`，阶段为 `reward-reserve`、`reward-complete`、`mission-complete`、`first-talk-reserve`、`first-talk-complete`。记录固定阶段、任务或奖励号、数值收据摘要、异常类型和连接场景，不输出原始收据键、异常正文或请求内容。

`Reward delivery incomplete` 记录部分或异常投递，说明预约仍为 pending。两者复用 `GameDiagnostics` 的每分钟首次详情、重复计数和超额汇总，不为轮询不断打印同一错误。收据摘要只用于定位日志，不用作交易身份或领奖校验。
