# 4.6 传统虚构叙事的战斗范围核验

原生两半场故事挑战的战斗创建时，冻结挑战实例、当前半场、进入点、场景对象、世界等级、队伍对象和角色次序、增益选择与已有分数，以及原始 NPC 的实体、组、配置、事件和全部战斗波次。消费报告前检查这些状态仍匹配，同时检查当前半场的基础/所选增益、回合上限和 10003 计分容器；不匹配时保留未消费的战斗。

故事挑战进行中，直接关卡、场景事件、花萼和元素重入都不能创建替代战斗。场景攻击只接受原始当前半场遇敌；范围不完整时不创建可结算战斗。4.2 保留原有入口行为，核心累计计分回归与 4.6 原始遇敌回归分别检查。

原生当前挑战的 round_count 使用故事回合上限，避免传统故事资源未提供 ChallengeCountDown 时返回 -5 并编码成无符号巨值。March7thHoney fe00bdbda3c28ca33d01f171566aa35b5ab95083 的 ChallengeConfigExcel.SetStoryExcel 将 TurnLimit 赋给 ChallengeCountDown，ChallengeStoryInstance.ToProto 返回该上限；本次只验证已支持 Normal 的两半场，未借此启用四回合 Fever。

36 项隔离 Java 回归使用 13 条完整原始关卡、事件、NPC、入口、平面和花萼记录，保留 6 个来源 Git blob SHA，资源提交为 724b139d8c9c32d12552eb95745a4fee72bfe48b。场景、正式角色和保存为明确测试替身。原实现 33 项行为断言失败；准备阶段的 Hash 字段适配和半场夹具问题没有计入。原生网络还独立复现了原实现错误接受直接故事事件的响应 0。

最终单次全量 11,783 项 Java（449 类）零失败，相关 63 项检查单独通过；累计 1,083 项 Python 结果沿用上一批，相关测试文件未改，本批没有重跑完整 Python 套件。3,226 个源码文件及 151 份协议快照通过。最终产物通过 38 次原生 KCP 请求、2 次正常关服与同一 UID 的一次 H2 进程重启：两半场直接事件都被拒绝，当前战斗和场景保持一致，原始遇敌仍能战斗、结算及合法重试；两半场 round_count 均为 5，重启后分别保留 12,000 / 28,000 与星数位 1。2,257 份来源文件未改动，目标历史没有预写，正式角色 1001 为控制台夹具。报告为 build/story-scope-verification.json，产物为 build/story-scope-certified.jar，SHA-256 为 e47391eb33019a2b96b0080bcf96ac57187e5c765e271e1b6a5afe96f22057ab。本批仍限于已支持的 Normal 两半场，分数来自已接受的客户端报告；Fever、Tierce、完整教程条件、服务端战斗演算和实际客户端界面继续待完成。
